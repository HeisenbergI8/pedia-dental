# Chunks: apps/api (backend build order)

The order to build the NestJS + MySQL backend in. It replaces the ~117 endpoints the MSW mocks serve today
(counted 2026-10-16) with real ones, feature by feature, without changing feature code in `apps/web`.

Every chunk is **Large**: it gets its own architect plan in `.claude/plans/`, built with `implement-plan`,
verified by `tester` and checked by `auditor`. Run `grill-me` first when a chunk has an open decision
(each chunk lists them). Each chunk depends only on chunks above it and ends with a **Done when** you can check.

**The spec for every endpoint is its MSW handler** (`apps/web/src/features/<name>/mocks.ts`, `apps/web/src/mocks/`)
and its rule in `apps/web/src/mocks/access.ts`. The rules for how to build it are in [CONVENTIONS.md](CONVENTIONS.md).

### Why this order

1. **Cross-cutting first, features second.** Tenant scoping, sessions, access, logging, transactions, the outbox
   and the test harness are built once (B1–B2), so every feature after them can't get them wrong.
2. **Follow the data's dependencies.** Accounts → staff and branches → patients → visits → everything clinical →
   scheduling → money → messages → the portal and the operator console, which read across all of it.
3. **Cut over as you go.** Each chunk ends with its endpoints served by the API and its mocks switched off in the web
   (per-feature passthrough, built in B1), so the product is always runnable and every chunk is tested for real.
4. **Riskiest rules early.** Tenancy and access (a leak is a privacy breach under RA 10173) come before any patient
   data reaches MySQL.

---

## ✅ Chunk B0: Skeleton (done, 2026-10-16)

NestJS 12, Prisma 7 + MySQL 8.4 in Docker, Zod-validated env, `GET /api/health`, `ZodValidationPipe`,
`HttpErrorFilter` in the web's error shape, HTTP tests without a database.

---

## Chunk B1: Platform foundation (~20 h) · Large

**Status (2026-10-16):** split in three. **B1-a done** (runtime core: context, clock, logs, tenant scoping, transactions,
audit). **B1-b done inside B2a** (`@pedia/seed`, `test:int` on MySQL with the two-clinics and deadlock proofs, CI,
the web's `hybrid` switch and `/api` proxy); `prisma db seed` lands in B2b. **B1-c open** (outbox, scheduler, storage).

**Goal:** the plumbing every feature relies on, built once, with no feature endpoints.

- **Request context:** one per request (AsyncLocalStorage), carrying request id, clinic, branch, user, roles and the
  operator flag. Services read it; nothing passes `clinicId` around by hand.
- **Tenant scoping in one place:** a Prisma client extension that adds `clinicId` (and `branchId` where the model is
  branch-scoped) to every read and write of a tenant model, and refuses a query on one when the context has no clinic.
  Platform models (accounts, sign-ups, prices, subscriptions) are explicitly unscoped. An unlisted model fails a test.
- **Ids and time:** string ids generated by the app (`cuid2`). One injectable `Clock` (the mock's `today()`), with
  timestamps stored in UTC and business dates as `DATE` in Asia/Manila.
- **Transactions:** a `runInTransaction` helper; services call it, controllers never do.
- **Outbox table and worker** (DB-polled, safe with several API instances via `SELECT … FOR UPDATE SKIP LOCKED`).
  Only the table, the worker and one no-op handler for now; messages arrive in B9.
- **Scheduled jobs:** `@nestjs/schedule` behind a DB lock, so one instance runs each job.
- **Structured logs** (pino): request id on every line, **no patient data in logs** (a redaction list, tested).
- **Audit trail** writer for the shared `audit` schema (append-only), called from services.
- **File storage interface** with a local-disk driver (the S3/R2 driver comes in B10).
- **Test harness:** an integration suite against a separate MySQL database (`test:int`, truncated between tests,
  run in CI), fixtures built from the web's seed, and a helper that signs a test in as any seeded user.
- **Seed:** `prisma db seed` ports the web's demo seed (Bulilit Smiles with two branches, Ngiti Kids) so the API
  demos with the same data.
- **Web: per-feature cut-over.** MSW passes through the paths of features the API serves (a list in the web's
  mocks), instead of the all-or-nothing `NEXT_PUBLIC_API_MOCKING`. In dev, the web proxies `/api` to the API.

**Decide first:** the cuid2 vs ULID choice; the DB-polled outbox vs Redis/BullMQ (recommended: DB-polled until
volume says otherwise); the seed strategy (port the TypeScript seed, or export the web's seeded JSON).

**Done when:** a test proves a query on a tenant model without a clinic in context throws, and that two clinics'
rows never mix; a job runs once with two API instances up; logs show a request id and no patient name;
`pnpm run check` stays DB-free and `test:int` passes in CI.

**Depends on:** B0.

## Chunk B2: Identity, sessions and access (~24 h) · Large — feature 16 (part)

**Goal:** real sign-in for staff and the operator, and the access gate, before any clinic data is served.

- Models: clinic account (tier, status, pause), branch, staff (roles, assigned branches, deactivated), credentials,
  sessions, operator users.
- Passwords and PINs hashed with argon2id. PIN lockout from `pinLockout` / `PIN_POLICY`.
- Sessions stored server-side (hashed token in MySQL, httpOnly `pd_session` cookie, same name as the mock), so the
  API stays stateless and any instance can serve any request. The branch cookie `pd_branch` is validated against the
  staff's branches.
- **Access guard:** a route → permission map mirroring `RULES` in `mocks/access.ts`, **deny by default**, decided only
  through `rolesCan` from `@pedia/shared`. A route with no rule answers 403 and names the route, like the mock.
  Suspended and paused accounts are refused at sign-in. The acknowledgement gate (`mustAcknowledge`) is enforced.
- Operator auth on its own cookie and routes, never sharing the clinic session.
- Rate limiting on every `/auth/*` and `/operator/auth/*` route.
- Endpoints: `/auth/login|logout|me|switch|password|acknowledgement`, `/operator/auth/*`, `GET /branches`,
  `GET /staff`, `GET /clinic`.

**Decide first:** the demo login (`/auth/demo-accounts`): keep it on demo deployments only, or drop it; the session
lifetime and idle timeout for a shared clinic device.

**Done when:** the web signs in against the API as every seeded role and as the operator; a route without a rule
answers 403; a staff member at two branches switches branch; a suspended account is refused; the mock's
`tenancy.test.ts` and access-control cases pass against the API.

**Depends on:** B1.

## Chunk B3: Clinic setup and Owner settings (~20 h) · Large — features 16 (rest), part of 2

**Goal:** everything a clinic configures, so clinical chunks have procedures, chairs, templates and limits.

- Clinic profile and branding (`brandColorProblem` validation), logo upload through the storage interface
  (with uploaded SVGs sanitised), branches (create, edit, archive, reopen), staff (add, deactivate, reactivate,
  email unique per account).
- **Tier limits as data**, enforced in the service (a second branch or a sixth login on Small is refused).
- Procedure catalog, chairs, note templates, message templates, `/clinic/usage`.

**Done when:** the Owner settings screens run fully on the API; the Small-tier limits are refused by the API itself;
`owner-settings.test.ts` passes against it.

**Depends on:** B2.

## Chunk B4: Patients and privacy consent (~24 h) · Large — features 1 and 18 (part)

**Goal:** the child's record, with the Data Privacy Act rules built in from the first row.

- Patients, guardians, emergency contact, allergies and alerts, consents. `POST /patients` takes
  `RegisterPatientInput` and requires the parent's consent.
- **`PatientView`:** contact data left out of every response without `patients.contact`, in one serializer.
- Patient list and search (indexed and paginated, see CONVENTIONS), summaries, duplicate detection, patient photo.
- Privacy choices and consent (`choiceDeclined`), the clinic's versioned privacy notice, public `/legal/notices`,
  and the agreements trail (append-only, `termsOutdated`).
- Audit entries for every read of a patient record.
- Indexes for search (name, birth date) scoped by clinic.

**Decide first:** search: MySQL full-text vs `LIKE` on indexed name columns (recommended: `LIKE` prefix now,
full-text when a clinic passes about 10k patients); encryption at rest for medical fields (column-level vs
volume-level).

**Done when:** creating, editing and searching patients works on the API; a front-desk user gets contact fields and
a dentist doesn't; a patient can't be registered without consent; every record view leaves an audit entry.

**Depends on:** B3.

---

## Chunk B5: Visits and the dental chart (~24 h) · Large — features 2 and part of 3

**Goal:** the clinical core, with append-only history guaranteed by the database layer.

- Visits (open, complete, the current visit).
- Chart entries: FDI teeth from `domain/teeth.ts`, surfaces and conditions, single and batch recording in one
  transaction. **Append-only:** no update or delete path exists; a correction is a new row with `supersedes`. The
  current chart is `deriveChart()` from `@pedia/shared`, the same code the web runs.
- "Chart as of visit X" and the per-tooth history.
- Indexes on (clinic, patient, recorded-at) so a long chart history stays fast.

**Done when:** caries on 74-O recorded in one visit and restored in a later one shows both in history; a correction
supersedes rather than edits (tested at the repository level); the chart matches the mock's for the seeded patients.

**Depends on:** B4.

---

## Chunk B6: Notes, growth, behavior and the treatment plan (~20 h) · Large — features 3, 9, 10, 11

**Goal:** the rest of the clinical record.

- Clinical notes from templates; signing makes a note read-only (enforced in the service, tested).
- Behavior tracking and growth and development (`PUT /visits/:id/growth`).
- Treatment plan and plan items (`PATCH /plan-items/:id`), progress derived, never stored.

**Done when:** signing a pulpotomy note makes it read-only on the API; the spec's example plan shows 3 of 6 done;
a habit stopped in a later visit shows correctly.

**Depends on:** B5.

---

## Chunk B7: Scheduling, follow-ups and Today (~24 h) · Large — features 4, 14, 15

**Goal:** the clinic's day, safe under concurrent booking.

- Appointments (book, move, status, check-in, no-show), chairs per branch.
- **No double-booking under concurrency:** the check and the insert happen in one transaction with a row lock on the
  chair's day (or a unique slot constraint), tested with parallel requests, not only in sequence.
- Appointment requests and handling them.
- Follow-up and recall due items from `DEFAULT_FOLLOW_UP_RULES` (data, not `if` statements); booking one clears it.
- `/reports/today` and branch filtering through `reportBranchFilter`.

**Done when:** two simultaneous bookings of the same chair and slot leave exactly one; an extraction signed today is
due in 7 days and booking it removes it; Today matches the mock for both demo clinics.

**Depends on:** B6.

---

## Chunk B8: Billing, payments and the financial dashboard (~22 h) · Large — features 7 and 8

**Goal:** money that is never wrong.

- Invoices, payments, deposits and credit. Integer centavos only; balances computed with `invoiceBalance`, never
  stored. Payments are append-only.
- **Idempotency keys** on every money-moving `POST`, so a retried request never records a payment twice.
- Every payment in a transaction that locks the invoice.
- `/payments`, `/reports/finance` with branch filtering, built on aggregate queries rather than loading every row.

**Done when:** the ₱8,500 / ₱5,000 / ₱3,500 example reproduces exactly; a payment POSTed twice with one key is
recorded once; the dashboard totals equal the sum of payments in SQL.

**Depends on:** B7.

---

## Chunk B9: Parent messages and real sending (~22 h) · Large — feature 5

**Goal:** messages actually leave, exactly once, only with consent.

- Message queue through the outbox from B1: booking queues a confirmation and a reminder in the **same transaction**
  as the appointment, so neither exists without the other.
- Providers behind an interface: Semaphore for SMS, an email provider, and a log-only driver for dev and tests.
- Retries with backoff, a dead-letter state, and delivery status shown in `/messages`.
- Consent enforced at queue time (`choiceDeclined`), templates from B3, birthday greetings and due-item messages as
  scheduled jobs.

**Decide first:** the email provider; sending hours (no SMS at night); the per-clinic SMS sender name and who pays for
SMS credits.

**Done when:** booking an appointment sends one confirmation through the log driver, exactly once across a worker
restart; a declined consent sends nothing; a failed send retries, then shows as failed.

**Depends on:** B8 (and B1's outbox).

---

## Chunk B10: Photos and documents (~16 h) · Large — features 12 and 13

**Goal:** files at scale, never through the API's memory.

- S3/R2 driver for the storage interface: **presigned uploads and downloads**, so files go straight between the
  browser and storage. Size and type checks, and keys scoped by clinic.
- Clinical photos (intraoral and extraoral consent enforced), before-and-after per tooth, patient photo.
- Document log (certificates, receipts), with the server checks (issuer, source, allergy) on the log request, before
  any PDF is built, like the mock.

**Decide first:** S3 vs R2, and the region (data residency for patient photos).

**Done when:** a photo uploads straight to storage and survives an API restart; one clinic can't read another's file
even with its key; a refused document produces no file.

**Depends on:** B9.

---

## Chunk B11: Parent portal and real parent accounts (~18 h) · Large — feature 6

**Goal:** parents sign in as themselves and see only their own family.

- Parent accounts and invitations (email or SMS through B9), sign-in on the B2 sessions.
- Ownership checks in the access guard: a parent reaches only their own children's records, and gets 403 otherwise.
- Portal reads (appointments, plan, invoices, documents), appointment requests, privacy choices.

**Done when:** a parent sees one child's data and gets 403 for another's, against the API; an invited parent signs in
for the first time and sets a password.

**Depends on:** B10.

---

## Chunk B12: Operator console, sign-ups and subscriptions (~26 h) · Large — features 16 (console) and 17

**Goal:** Primolar runs its own business on the API.

- Operator console: accounts, tiers, Owners, suspend and reactivate, branding for "Design it for me", usage, the price
  list.
- Public sign-ups: multipart form with files through storage, status by reference, record payment, fix, reject,
  approve → `createClinic` in one transaction.
- Subscriptions: due dates only from `subscriptionDueOn`, states from `subscriptionStatus`. **Settling overdue
  accounts becomes a daily scheduled job** (plus a check at sign-in) instead of the mock's settle-on-every-request.
- Primolar invoices.

**Decide first:** PayMongo checkout and auto-charging now or later (recommended: a separate chunk after B13; this
chunk keeps payments recorded by hand, like the prototype).

**Done when:** a sign-up submitted, paid and approved becomes a working clinic whose Owner can sign in; a clinic
approved on the 31st is due on the 30th next month; an account 7 days overdue pauses itself after the nightly job.

**Depends on:** B11.

---

## Chunk B13: Production readiness and full cut-over (~24 h) · Large — feature 18 (rest)

**Goal:** the web runs with the mocks off, on infrastructure that can grow.

- **Mocks off:** `NEXT_PUBLIC_API_MOCKING=disabled` everywhere, and the web's handler tests ported to API tests.
- **Production build:** a bundled build (the SWC runtime loader is dev-only), a multi-stage Dockerfile, `prisma migrate
  deploy` as a release step.
- **CI:** typecheck, unit, integration against MySQL, and a migration check (schema drift fails the build).
- **Operations:** health and readiness probes, metrics, error tracking, daily backups with a tested restore,
  encryption at rest, secrets in the platform's store.
- **Hardening:** security headers (helmet), CORS locked to the web's origins, rate limits, a dependency audit, and a
  load test against the busiest endpoints (Today, patient list, booking).
- **Data Privacy Act operations:** data export and deletion requests, retention, and the NPC registration notes.
- **Deploy:** the API and MySQL on a managed host (decide which), the web pointed at it.

**Decide first:** the hosting (managed MySQL is the default: RDS, PlanetScale, or a VPS), and the backup retention.

**Done when:** the client demo script (`DEMO_SCRIPT.md`) runs end to end with the mocks off on the deployed API;
restoring last night's backup to a fresh database works; the load test meets its targets.

**Depends on:** B12.

## Later (own chunks, after B13)

- PayMongo checkout and automatic monthly charging; BIR official receipts.
- Read replicas and caching (Redis) when the load test or real traffic says so, not before.
- Per-clinic web addresses; operator impersonation with an audit trail.
- Patient merge (after duplicate detection in B4).

## Order at a glance

```
B0 Skeleton ✅
 └─ B1 Platform foundation (context, tenant scoping, outbox, jobs, logs, audit, storage, test harness, cut-over switch)
     └─ B2 Identity, sessions & access
         └─ B3 Clinic setup & Owner settings
             └─ B4 Patients & privacy consent
                 └─ B5 Visits & dental chart
                     └─ B6 Notes, growth, behavior & plan
                         └─ B7 Scheduling, follow-ups & Today
                             └─ B8 Billing, payments & dashboard
                                 └─ B9 Parent messages & real sending
                                     └─ B10 Photos & documents
                                         └─ B11 Parent portal & parent accounts
                                             └─ B12 Operator console, sign-ups & subscriptions
                                                 └─ B13 Production readiness & full cut-over
```

The order is strict for B1–B5. After B5, B6, B7 and B10 touch different tables and can be reordered if the client
needs one sooner; B8 needs B7 (appointments create invoices), and B11–B12 read across everything.

B1, B2 and B5 carry the most risk (a tenancy leak, an access hole, a lost clinical entry). If time gets tight, cut scope
from B12's console polish and B13's load test, not from those.
